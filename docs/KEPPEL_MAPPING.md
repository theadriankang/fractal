# Keppel "AI HARVEST" — requirement → Fractal feature mapping

Maps every requirement in the Real Estate Track challenge brief to the exact Fractal feature, file or screen that answers it. Chosen Intelligence Pills (domains): **Technical Services, Energy Optimisation, Asset Operations, Tenant Experience, Leasing, Sustainability** — all six (`src/data/taxonomy.js`), so the platform isn't scoped to just one.

## What the Solution Should Solve

| Requirement | How Fractal answers it |
|---|---|
| **Capture expert know-how**, including undocumented knowledge | Two capture paths: (1) passive — any contributor's chat message ≥12 words is run through an extraction pass (`backend/app/capture/extract.py`) that proposes new/revised Expertise with a verbatim quote as evidence; (2) active — the Meeting Recorder (`src/pages/MeetingRecorder.jsx`) transcribes a live conversation with an expert and saves it as a source. |
| **Turn know-how into reusable, governed intelligence** | The Expertise object (`src/data/expertise.js` schema) structures each pill with `summary`, `whenToUse`, `knowledge[]`, `decisionLogic[]`, `guardrails[]`, `escalation[]`, an `owner`/`reviewer`, and a version history — not a one-off chat answer. |
| **Apply specialist AI support** | `POST /api/chat/stream` retrieves the top-matching *approved* Expertise for the prompt (`backend/app/retrieval/index.py`, hybrid pgvector + keyword search) and grounds the model's system prompt with it (`backend/app/prompts.py`) — any of the 12 connected models (Claude, GPT, Gemini, Grok, Hunyuan, DeepSeek) can apply the same governed knowledge. |
| **Coordinate across domains** | Retrieval spans all six domains, and chat now shows it: each "Expertise applied" chip carries its domain, and an answer grounded in more than one domain says "Drew on: Energy Optimisation, Technical Services" (`domainsCoordinated` in the `/api/chat/stream` meta event, as in Data Insights). When a question names two areas or a trade-off, or the experts behind it actually conflict, chat adds **Experts weighed together** under the answer (`POST /api/expertise/weigh`, `auto: true`): one approved Expertise per domain (two if the same domain's playbooks are linked), showing each expert's view, where they agree, where one domain's idea runs into another's rule (quoting that approved rule), the deciding factor, and suggestions that keep every expert's stance visible. Plain questions get no weighing. |
| **Keep people in control** | See "Human-supervised" below — every write to governed data requires an explicit human action (submit → review → approve), and the system prompt (Appendix A) instructs models to recommend, never to claim an action was performed. |
| **Learn through governed feedback** | A 👍/👎 rating on any answer feeds `POST /api/responses/{id}/rating` and records the Expertise version it judged. A 👎 with a correction goes to `POST /api/loop/correction`: Claude diagnoses it (outdated, missing step, out of scope, or the answer ignored the Expertise) and proposes the minimal change — rewriting the wrong step in place — plus a test question; repeat reports merge into one proposal. In the Review Queue, **Test change** (`POST /api/loop/test`) re-asks saved questions with the current and proposed version and grades each answer blind, so the reviewer sees what the change fixes or breaks before approving. Per-version 👍 rates flag slipping Expertise and suggest a rollback. Nothing changes live Expertise until a Reviewer approves it (see `docs/FEEDBACK_LOOP.md`). |

## The Solution Should Be

| Criterion | Where it's shown |
|---|---|
| **Human-supervised** | Nothing reaches "approved" without a person: `POST /api/expertise/{id}/submit → approve` requires a `reviewer` role (`backend/app/governance.py`, enforced server-side, not just hidden in the UI). |
| **Transparent** | Every answer that used Expertise shows an "Expertise applied: *name* vN" chip; the `meta` SSE event and chat message store the exact Expertise id+version used, and Auto routing shows its category + reason ("Auto · Operational reasoning"). |
| **Accountable** | Every Expertise has an `owner` and, once approved, a `reviewer`; every governance action writes an audit row with the actor's identity (`audit_log`, `GET /api/audit`). |
| **Reliable** | Drafts/in-review Expertise are never injected into a model prompt (`backend/app/retrieval/index.py` filters `status='approved'` only) — only reviewed, versioned content can influence an answer. Feedback (👍/👎) tracks a `successRate` per Expertise over time. |
| **Reusable** | Once approved, an Expertise is matched and applied automatically to *any future conversation* across the org, on *any* connected model — not re-typed per conversation. |
| **Scalable** | The taxonomy is domain × topic × asset type (`ASSET_TYPES = [Office, Data Centre, Logistics, Retail]`), so one Expertise can be tagged for multiple asset types, and new domains/topics are additive, not a schema change. |
| **Governed** | Full lifecycle: draft → in_review → approved → (deprecated / rolled back), every transition reviewer-gated and audited — see the Expertise-lifecycle diagram in `docs/ARCHITECTURE.md`. |
| **Portable** | Expertise content is plain structured data (JSON fields in Postgres) owned by the organisation, independent of any one model — the same record is used to ground Claude, GPT, Gemini, Grok or Hunyuan interchangeably; it can be exported via the API with no vendor lock-in. |
| **Version-controlled** | Every approval bumps a semantic version and snapshots the prior content to `expertise_versions`; `POST /api/expertise/{id}/rollback {version}` restores any prior snapshot as a new version, never a destructive overwrite. |
| **Secure** | Role-based access (`reviewer` / `contributor` / `intern`) is enforced **server-side** on every governance endpoint, not just hidden in the UI (`backend/app/auth.py`'s role checks). Requests authenticate with a real Supabase session: the front end signs in via `supabase.auth.signInWithPassword` and sends the resulting JWT as `Authorization: Bearer`, and the backend verifies it against the project's own signing keys (`backend/app/auth.py` — ES256 checked against Supabase's JWKS, with a legacy HS256 shared-secret path for older projects) before trusting the `sub` claim as the caller's identity. |
| **Clearly bounded** | Every Expertise explicitly separates `knowledge`/`decisionLogic` (what to do) from `guardrails` (what must never be done) and `escalation` (when a human specialist must take over); the system prompt instructs the model to prefix escalation-condition answers with "⚠️ Escalate:" and to label anything beyond approved Expertise as "General guidance (not from approved Expertise)". |

## Solution Diagram — all eight required points

The brief requires the diagram to show these eight things. Each row below is the real
answer, grounded in the actual feature/file, not aspirational copy.

| # | Point | Answer |
|---|---|---|
| 1 | The specific business problem | Critical operational know-how (e.g. "which fault pattern means it's the lift door contacts, not the controller") lives in a few experts' heads, is applied inconsistently across assets, and is lost when they leave — see `docs/PROJECT_CONTEXT.md` → "What Fractal is". |
| 2 | Whose expertise, and how undocumented knowledge is obtained | Domain experts (contributors scoped to their domain, e.g. a Technical Services engineer) — captured passively from their normal chat usage (`backend/app/capture/extract.py`), or actively via the Meeting Recorder when interviewing an expert who doesn't write things down (`src/pages/MeetingRecorder.jsx`). |
| 3 | How captured expertise becomes reusable | It's promoted from a raw quote into a structured, versioned Expertise record (not left as a chat transcript), matched by semantic + keyword search and auto-applied to any future relevant question — see the lifecycle diagram in `docs/ARCHITECTURE.md`. |
| 4 | How an Asset Operations Manager uses/supervises it | They see the Review Queue (pending drafts/proposals to approve), the Expertise catalog (browse what's approved, by domain/topic/asset type), the "Expertise applied" chip + "Drew on" / Weigh panel + escalation warnings on every answer, and the Audit Log for full traceability. |
| 5 | Why this is more than a chatbot or information-retrieval tool | A chatbot/RAG tool retrieves and answers; it doesn't change state or get better. Fractal does three things retrieval alone doesn't: (a) it **writes back** — a correction or a captured insight becomes a governed artifact (a Proposal, a new draft Expertise) that outlives the conversation, not just an answer that's thrown away; (b) it **reasons across sources of judgement, not just documents** — when two domains' approved guidance actually conflicts, the Weigh engine (`backend/app/weigh/engine.py`) surfaces the disagreement and the deciding factor, rather than silently picking one passage; (c) it **acts on data proactively, not only on request** — Data Insights (`backend/app/insights/`) ingests a raw dataset unprompted-per-row and generates the analysis, flags the top issues, and asks "should we talk about this" rather than waiting for a query. None of that is "search, then answer" — it's capture → structure → govern → apply → re-capture, a closed loop a chatbot has no mechanism for. |
| 6 | How feedback, outcomes and new expertise are reviewed, validated, versioned and approved **after deployment** | This runs continuously, not as a one-time setup: every chat answer carries 👍/👎 (`POST /api/responses/{id}/rating`); a 👎 with a correction becomes a precise revision Proposal in the Review Queue (`POST /api/loop/correction`), which the reviewer can test old-vs-new on saved questions before approving (`POST /api/loop/test`), rather than silently changing anything. A Data Insights report can be captured the same way — "Save this analysis as Expertise" turns a finding or a Q&A exchange into a draft/proposal (`src/pages/Insights.jsx`'s `CaptureInline`). Every Proposal needs a Reviewer (never the original author — four-eyes, `backend/app/governance.py`) to approve before it reaches `approved` status; approval snapshots the prior version (`expertise_versions`) and bumps a semantic version, so nothing is a silent overwrite, and `POST /api/expertise/{id}/rollback` can restore any prior snapshot. Every transition writes an `audit_log` row with the actor's identity (`GET /api/audit`), so there's a complete after-the-fact record of what changed, who approved it, and why. |
| 7 | How the concept extends from one asset/domain to multiple assets, business units or enterprise environments | The taxonomy is domain × topic × asset type (`src/data/taxonomy.js`): adding a new domain, topic or asset type is additive data, not a schema or code change, and one Expertise entry can already be tagged across multiple asset types (Office, Data Centre, Logistics, Retail). The platform already runs all six Keppel domains at once, not one pilot vertical. Beyond real estate: Data Insights is explicitly domain-agnostic — it takes any tabular upload (energy, cost, tickets, occupancy, anything) and adapts its own shape-detection to whatever the data looks like, which is the same "reusable capability, not a one-off" principle the brief asks for, demonstrated outside the real-estate-specific examples. And because Expertise is plain structured data in Postgres, not vendor- or model-specific, the same governed record already grounds 12 different connected models — extending to a new business unit doesn't mean re-platforming, it means pointing a new client at the same API. |
| 8 | A credible path to implementation using current or near-term technology | This isn't a concept deck — it's deployed and running today on production infrastructure: FastAPI on Google Cloud Run, Postgres + pgvector + Auth on Supabase, a React/Vite frontend on Vercel, real calls to Claude and five other models via OpenRouter (see the trust-boundary diagram in `docs/ARCHITECTURE.md`). Every governance rule (reviewer-only approval, four-eyes, server-side role checks) is enforced in the backend today, not sketched as a future control. The one deliberate trade-off (local `fastembed` embeddings instead of a hosted embedding API, to keep the core retrieval loop at zero marginal cost) is documented with its cost in `docs/ARCHITECTURE.md` → "Key design trade-offs" — nothing here depends on a capability that doesn't exist yet. |

## Known limitations (said plainly, not hidden)
- **Meeting Recorder transcription is browser-only today**: `backend/app/config.py`'s `TRANSCRIBE` flag (`browser` / `tencent-asr` / `whisper`) exists for a server-side transcription path, but only `browser` (the Web Speech API, client-side) is implemented — the other two are documented placeholders (see the flag's own TODO).
- **Expertise embeddings run locally (fastembed), not through a hosted embedding API** — a deliberate trade-off for zero marginal cost and no outbound dependency on the core retrieval loop (see "Key design trade-offs" in `docs/ARCHITECTURE.md`); it trails a model like `text-embedding-3-small` on embedding quality, which the hybrid keyword-boosted score partly compensates for.
